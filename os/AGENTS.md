# Memory workspace rules

Read these rules before working in this workspace. Replace intended setup placeholders only from the owner's answers.

## Session start

1. Read 90_memory/core.md and 01_projects/PROJECTS.md.
2. Use the routing table. Read only records needed for the task.
3. Before project edits, read its handoff.md and inspect existing work.
4. If the project has no records, create them from the templates before substantive work.
5. If a review is overdue, report it and follow the review checklist within the authorized task scope.

Add a specific routing row when a new memory topic has recurring content.

## Map and filing

00_inbox: new material and unresolved decisions.
01_projects: project folders and the generated PROJECTS.md dashboard.
02_areas: ongoing responsibilities and standards.
03_resources: templates, scripts, references, and skills-custom.
90_memory: durable preferences, corrections, and decisions.
99_archive: preserved inactive material, read-only unless restoration is authorized.

File by intended use: outcome to project; ongoing standard to area; reusable method to resource; inactive material to archive. If unclear, leave an inbox note and ask. Do not treat an arbitrary filename as permission to move confidential content.

Use YYYYMMDD_keyword_type.ext for new managed documents. Preserve required code and tool filenames. Prefer kebab-case and shallow folders. Add subfolders when actual content justifies them; three related files is a starting threshold. Register new categories in this map.

## Writing

Use ASD-STE100 principles for all skills, instructions, and technical writing, including private work. Use one term per concept, active voice, explicit conditions, and one action per instruction. Preserve facts, uncertainty, thresholds, and behavior. Do not claim formal certification. Creative output follows its own requested voice.

## Autonomy and privacy

Perform small, reversible work already authorized by the task. Update current records and report the result. Ask before deletion, replacing an approved deliverable, changing these rules, external sharing, remote configuration, or other hard-to-reverse work unless the owner already approved that scope.

Keep credentials outside the workspace. Review actual content before sync, backup, or publication. Follow the owner's device, organization, and AI-tool policy. Separate work and personal records when required. Never infer that a blank starter template makes later user content safe to share.

## Project ownership

Read Current owner in the project handoff before editing. If another session owns it, do not take over without permission. When owner is none, claim the project for this session. Preserve unrelated uncommitted changes. Work sequentially on shared project records.

## End of session

For each touched project, update handoff.md and append a log entry. Keep the handoff at 60 lines or fewer and retain Goal, Now, Verified, Blocked, Next, Tried and failed, Constraints, and Pointers. Record tests and limitations. Release ownership when stopping.

Run the dashboard after changing project state. Record explicit corrections with date, evidence, and scope. If Git is configured and a commit is authorized by the workspace owner, inspect and commit only the intended files. Do not push from a local save operation alone.

## Wrap-up and review

When the owner asks to wrap up, use 03_resources/templates/project-wrapup.md. Treat finish as completion only when the goal is achieved. Keep pause distinct from completion. Review overdue items using 03_resources/templates/os-reviews.md. Scripts report structural findings; assess their meaning before changing content.

## Multiple clients and migration

AGENTS.md is the rule source. Other client instruction files are short pointers with necessary client-specific settings. Verify that each configured client actually loads this file. Platform memory is supplementary, not a substitute for saved project records.

Keep a restore record for external tools and configuration. Do not place credentials in that record. Keep separate workspaces when confidentiality boundaries require them. Copying a method does not authorize transferring private memory.
