# Workspace OS

Maintain saved rules, memory, and project state in one workspace. Continuity depends on saved records, available tools, and verified instruction loading. Do not promise automatic or loss-free memory.

## Choose the operation

| Operation | Read |
|---|---|
| New workspace or first interview | references/bootstrap.md |
| New category, domain, or client | references/extend.md |
| Health, reviews, or method changes | references/maintain.md |
| Migration or external dependencies | references/portability.md |

Read AGENTS.md and the current project handoff before editing. Use the owner's confirmed facts. Keep placeholders as setup instructions until answered.

Keep one source per record. Use generated mirrors only when a real external dependency requires them. Document the regeneration and drift check. A manually maintained copy needs an explicit owner and update method.

Use the existing categories. New project records contain README.md, handoff.md, and log.md. Create working, reference, and deliverables directories when needed. Keep handoff.md at 60 lines or fewer.

Use ASD-STE100 principles for skills, instructions, and technical writing. Apply this baseline before release preparation. Keep creative output in its requested voice. Do not shorten away behavior, exceptions, or uncertainty.

For a correction, record date, evidence, and scope. Keep project taste in the project. Promote a shared rule only from explicit instruction or repeated verified evidence. When changing rules, preserve the prior record and update an appropriate check or review step.

Keep credentials outside the workspace. Do not assume private facts are publishable. Inspect actual files before any sync or sharing. Optional Git and client installation follow the owner's authorization.

At session end, save current state and next action. Report exact paths, performed checks, and limitations. Verify a fresh-session resume before claiming the method works in a new client.
